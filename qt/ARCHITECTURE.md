# Pilcrow Qt client — architecture and conventions

The native desktop client: **PySide6 (Qt 6), Qt Widgets, CPU rasterised**, for machines with no
GPU where a browser engine crawls. It replaces the WebKitGTK shell on Linux (and can run on Windows
and macOS). It talks to the unchanged Node server over the same WebSocket JSON-RPC the web interface
uses, so `server/` is never touched and the web interface stays for `pilcrow --server` over SSH.

Everything the web interface does, this client does, with the same information architecture, the
same words, the same tokens (colours, type scale, radii) and the same feel. Read the React source
in `web/src` for the behaviour of anything you build: it is the specification.

## Rules

- **Python 3.9+** (Ubuntu 22.04 ships 3.10). `from __future__ import annotations`; no `match`,
  no `X | Y` at runtime. Type hints everywhere; dataclasses for records.
- **PySide6 only** (`from PySide6.QtWidgets import …`). No PyQt, no Qt Designer `.ui` files, no
  QML, no QtWebEngine. Widgets are built in code with layouts.
- **No GPU assumptions.** Nothing may need OpenGL. QGraphicsView is fine (software). Effects are
  cheap by design: flat surfaces, hairlines, no blur. Animations use QPropertyAnimation /
  QVariantAnimation with the spring curves from `theme.py` (`spring_soft`, `spring_snappy`,
  `spring_bouncy` as QEasingCurve custom types); honour `Store.reduced_motion`.
- **`lib/` is pure.** Nothing in `qt/pilcrow_qt/lib` imports Qt. It mirrors `web/src/lib` function
  for function; the TypeScript tests in `test/unit` are ported to `qt/tests/test_lib_*.py`.
- **State flows one way.** Widgets read from `Store` and call its actions; they never call `rpc`
  directly except through a Store action. `Store` emits Qt signals; widgets connect and re-render
  the part that changed. Transcript items are mutable objects with a `rev` counter, exactly like the
  web model; a widget keeps the `rev` it drew and skips when unchanged.
- **App-wide signals are bound, not connected.** `Store` and `theme.theme` outlive every widget, and
  a lambda connected to their signals keeps firing after its widget is deleted (then crashes on the
  dead C++ object). Always `from ..ui.signals import bind` and write
  `bind(store.sessions_changed, self, self._on_sessions)` — it disconnects when `self` is destroyed.
  Signals of a child widget (a button's `clicked`) may be connected directly.
- **Theme tokens, never literal colours.** `theme.tokens().text_2`, `theme.tokens().accent` …
  Widgets that paint use the tokens (`paint_box`, `Box`, `Pill`, `Btn` in `widgets/ui`); widgets
  that Qt paints take their colours from their palette: the application palette carries the theme
  (`theme.palette`), and `theme.tint(w, fg="text_3")` / `tint(w, bg="chrome")` gives one widget
  other roles from the tokens (a token name, a blend such as `"fill_2/canvas"`, or a function of
  the tokens), re-applied on every switch. Never put a colour in a stylesheet: the application
  stylesheet is static and names colours only as `palette(role)`; a per-widget stylesheet may
  carry geometry and fonts, and `palette(role)` only on the native fields, combos and scrollbars
  that `theme.repolish` polishes again after a switch. Switching theme swaps the palette, re-tints,
  repolishes those, and emits `theme.changed`; custom painters repaint on it.
- **Fonts**: `theme.font_ui(size)`, `theme.font_mono(size)`; sizes come from the type scale in
  tokens (`fs_ui=13`, `fs_body=14.5`, `mono=12.5`…). Chinese text falls back to the system CJK face
  through Qt's own substitution; do not hardcode families.
- **Icons**: `icons.icon("square-terminal", color=tokens.text_2, size=14)`; names are Lucide's
  kebab-case names. `icons.pixmap(...)` for painting.
- **Words**: copy the exact strings from the React components (titles, hints, empty states,
  button labels). Shortcuts too (App.tsx, Composer.tsx, Sidebar.tsx).
- **Accessibility**: every button has an accessible name (`setAccessibleName`) matching its title
  or tooltip; keyboard focus order follows the layout.
- **Tests**: every widget module gets a pytest-qt test that builds it against the mock server (or
  a fake Store) and asserts on structure and text, the way `test/e2e/run.mjs` does for the web.
  `python -m pytest qt/tests` must pass offscreen on Linux and Windows.
- **Style**: black-compatible formatting (120 columns), `ruff` clean, docstrings that say what a
  thing is for, comments that say why, no commented-out code.

## Runtime shapes

The server's messages and state are documented in `web/src/lib/types.ts`; the client keeps them as
plain `dict`s (JSON as it arrives) at the boundary and converts to dataclasses only inside `lib/`
(transcript items) and `store.py` (Runtime, SessionSummary). Method names and event names are the
strings in `server/main.js`; `rpc.call("session.send", {...})` returns a `Call` with `.then(fn)` /
`.catch(fn)`; `rpc.on("session.msgs", fn)` subscribes to an event.

## Running

```
pip install -r qt/requirements.txt
node test/mock/mock-server.mjs 5300            # or a real Pilcrow server
python -m pilcrow_qt --url http://127.0.0.1:5300/
```
`PYTHONPATH=qt` or `pip install -e qt` makes the package importable.
